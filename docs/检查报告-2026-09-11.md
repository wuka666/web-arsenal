## 四、P0 详述

### 1. 18 套方案 demo 的调参把布局写坏（54 个控件）

**现象**
在方案库里展开任意一套旧方案（`f001`–`s205`，共 18 套），拖动「圆角」「间距」「基础字号」三个滑杆，页面不会按你调的值变好看，而是直接塌掉：圆角变直角、标题缩回正文大小、内边距归零。

**证据**

调参监听写死在 demo 里，且没有补单位（`assets/demos/方案-大色块分区.html:63`，18 个文件的这一行完全相同）：

```js
<script>addEventListener('message',e=>{const d=e.data;if(d&&d.type==='param')document.documentElement.style.setProperty('--'+d.key,d.value)});</script>
```

而 `index.html:695-696` 下发的是 `parseFloat` 之后的纯数字：

```js
const v = parseFloat(input.value);
current[p.键] = v; sendParam(iframe, p.键, v); refresh();
```

同一份 demo 的 CSS 里这些变量是带单位的（`assets/demos/方案-大色块分区.html:8`、`:11`、`:16`、`:19`）：

```css
:root{--yuanjiao:14px;--jianju:10px;--zihao:15px;--yinying:30;--faguang:0}
.wrap{padding:calc(var(--jianju)*2) var(--jianju);}
.cta{border-radius:var(--yuanjiao);}
.hero h1{font-size:calc(var(--zihao)*2.6);}
```

真实 Chrome 实测（把 `--yuanjiao` 写成 40、`--jianju` 写成 40、`--zihao` 写成 30 后读计算样式）：

| 文件 | 调参前 | 调参后 | 结果 |
|---|---|---|---|
| `方案-大色块分区.html` | `--yuanjiao:14px`；按钮圆角 14px；`h1` 字号 39px；容器 padding-top 20px | `--yuanjiao:40`（无单位）；按钮圆角 **0px**；`h1` 字号 **16px**；padding-top **0px** | 坏 |
| `方案-焦点型Hero.html` | 圆角 16px；`h1` 字号 41.6px；padding-top 28px | 圆角 **0px**；`h1` 字号 **16px**；padding-top **0px** | 坏 |
| `方案-定义型首屏.html`（对照组，监听写对了） | 圆角 10px | 圆角 **40px**；`h1` 字号 41.6px → **78px**；padding-top 16px → **40px** | 正常 |

对照组之所以正常，是因为它显式补了单位（`assets/demos/方案-定义型首屏.html:79-81`）：

```js
r.setProperty("--yuanjiao", state.yuanjiao + "px");
r.setProperty("--jianju", state.jianju + "px");
r.setProperty("--zihao", state.zihao + "px");
```

逐条核对（数字默认值 + CSS 声明带单位 + 裸写值）：受影响的坏参数 54 个，固定在每套的 `yuanjiao` / `jianju` / `zihao` 三个；另外 36 个数字参数（`yinying` / `faguang` 等）因为 CSS 里写成 `calc(var(--x)*1px)`，仍可用，不算坏。

**为什么算问题**
违反 **规矩 10①**：「参数键须与代码内 CSS 变量名一致，demo 支持 `postMessage({type:'param',key,value})` 调参，**调了要实时看到变化**」。实测结论是「调了看到的是坏掉的变化」——圆角、间距、字号三个滑杆是方案库最显眼的交互（README 也把「拖滑块调参」写进了卖点），现在 18/20 套不可用。

**修复方向**
在两个落点里改，选一个：

- 方案 A（推荐，改 18 个 demo）：把第 63 行换成带单位白名单的写法，只给 `yuanjiao` / `jianju` / `zihao` 补 `px`：
  ```js
  addEventListener('message', e => {
    const d = e.data; if (!d || d.type !== 'param') return;
    const UNIT = { yuanjiao: 'px', jianju: 'px', zihao: 'px' };
    document.documentElement.style.setProperty('--' + d.key, d.value + (UNIT[d.key] || ''));
  });
  ```
  同时把 `data/方案.js` 里对应 18 套的 `代码` 字段同步替换（不改会立刻造成代码字段与演示页不同步）。
- 方案 B（改 1 个文件）：只改 `index.html` 的 `sendParam`，按参数名补单位再下发。风险是把「该发数字的纯计算参数」也补成 px，需要一张白名单，且下载走的 `代码` 字段仍缺单位。

**工作量与风险**
方案 A 约 2 小时（18 个 demo + 18 套数据的 `代码` 字段）。风险是批量替换写坏 demo —— 回滚方式：动手前先 `git stash` 或 `git commit` 一次快照，出问题 `git checkout -- assets/demos data/方案.js` 即可还原；改完必须跑附录 A 的 `audit8.js`（应输出「坏参数 0」）和 `probe`（应看到圆角随滑杆变化）。

### 2. 生成方案时 34/92 条素材被静默丢弃

**现象**
把素材加入购物车、点「生成方案」，提示词里只会出现一部分素材。比如你只勾了 `s204 logo 墙`、`v108 骨架落位`、`v113 半屏停留`，生成出来的提示词里一条素材都没有。

**证据**

`index.html:865-885` 的分组字典按 `元素` 当键来筛：

```js
const groups = { "字体": [], "颜色": [], "版面": [], "动效": [], "留白": [] };   // 868 行
chosen.forEach(it => {
  (it.元素 || []).forEach(e => { if (groups[e]) groups[e].push(it); });           // 870 行
});
const labels = { "字体": "【文字与字体】", "颜色": "【颜色与氛围】", "版面": "【版面与布局】", "动效": "【动效与交互】", "留白": "【留白与层级】" };  // 875 行
```

而 `元素` 的实际取值是另一套词汇（实测全库去重）：

```
视觉(35) | 动效(58) | 构成(17) | 反馈(17) | 布局(4) | 3D·粒子(5)
```

两套词只有 `动效` 一个交集。实测结果：`字体` / `颜色` / `版面` / `留白` 四个分组恒为 0，且 `34/92` 条素材因为 `元素` 里没有「动效」而完全进不了提示词，例如 `s204`（元素 `["视觉"]`）、`v108`（`["视觉"]`）、`v132`（`["构成","反馈"]`）、`v133`（`["构成"]`）。

**为什么算问题**
按本轮分级定义，这属于 P0「数据会静默丢失/误导」：用户点了「生成方案」，程序没有任何提示地丢掉三分之一的素材，导出的提示词和用户的选择不一致。宪法里没有一条直接管这个映射（不是违宪条款），是纯功能缺陷，所以按 P0 报。

**修复方向**
改 `index.html:868-875` 一处：把 `groups` 的键换成 `元素` 的真实取值，`labels` 同步改中文标题。建议：

```js
const groups = { "视觉": [], "动效": [], "构成": [], "反馈": [], "布局": [], "3D·粒子": [] };
const labels = { "视觉": "【视觉与氛围】", "动效": "【动效与交互】", "构成": "【构成与版面】",
                 "反馈": "【反馈与状态】", "布局": "【布局与结构】", "3D·粒子": "【3D 与粒子】" };
```

改完 6 个分组覆盖 92/92 条，且一条素材会同时出现在它命中的多个分组里（这与现在的行为一致）。如果不想让同一素材重复出现，改成「按 `元素` 主类归组一次」：`const main = (it.元素||[])[0]`。

**工作量与风险**
20 分钟。风险：分组标题变了之后，历史生成的提示词文案不同（无兼容问题）。回滚：只改了一个文件的一处对象，`git checkout -- index.html` 即可。复验：勾选 `s204` 一条，点「生成方案」，`planText` 里必须出现 `s204` 的标题。

**证据**

```
- speed 流动速度 / count 光条数量 / thick 粗细 / round 圆角 / color 主色
```

## 七、P3 建议（可做可不做）

> 本节全部为优化建议。**不做也不算缺陷**，不引入任何违规判定。

### 13. 卡片无法用键盘展开

真实 Chrome 实测：`.card` 的 `tabIndex = -1`、`cardFocused = false`、`role = null`。卡片里能 Tab 到的是 15 个内部控件（按钮/滑杆/输入框），但「点卡片展开」这个主入口只能鼠标点（`index.html:653-656` 绑定的是 `click`）。另外全站 `aria-*` 属性数量为 0，也没有任何 `:focus-visible` 样式规则。

**建议**：给 `.card` 加 `role="button"`、`tabindex="0"`、`aria-expanded`，并监听 `Enter`/`Space`；`iframe` 的 `title` 已经全有（实测 `iframeTitleOK: true`），这一项不用改。工作量约 1 小时。

### 14. 全站没有 `prefers-reduced-motion` 降级

实测：113 个 demo 中含该媒体查询的 **0/113**；`index.html` 内也是 0 处。这个库的核心卖点就是动画，前庭敏感用户目前没有开关。

**建议**：至少在 `index.html` 里给卡片悬停位移（`index.html:124` 的 `transform: translateY(-2px)`）和 `scrollIntoView({behavior:'smooth'})`（`index.html:668`、`:1046`）加降级。demo 逐个加成本高，可以只在页面级加。

### 15. 方案弹窗无 Esc、无焦点管理

真实 Chrome 实测：
```
{"opened":true,"focusInModal":false,"stillOpenAfterEsc":true,"closedByButton":true}
```
